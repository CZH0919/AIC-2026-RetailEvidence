## 一次任务怎么走

1. 原有导入服务保存原文件、`raw.parquet` 和映射后的 `canonical.parquet`。
2. 店主核对数据范围、完整性、重复候选与重叠策略，先提交 `check_only`。
3. 确认后，`POST /api/projects/{project}/sales/runs` 在原 `AnalysisRun` 中保存任务。
4. 原 `TaskRunner` 领取任务，解析指定的字段版本并交给隔离 worker。
5. `retail_engine` 检查来源哈希、执行汇总，必要时调用 `sales_mining`。
6. 原发布机制保存清单与文件哈希，原运行 API 返回结果。行动备注另存 `SalesRecord`，不修改原报告 JSON。

CPU 仍受原队列、单 worker、两线程、8 GiB 内存与超时约束。网页和 AI 仅监听回环端口；没有新增公网暴露或多租户权限系统。

## 数据与结果合同

- 旧映射缺少 `record_kind` 时按 `transactions` 处理。汇总表不得映射订单总额或伪造订单号。
- 月汇总必须明确 `summary_month`。缺每日记录时没有每日图、日级预测或异常模型。
- 金额缺失为 `null`，不是零。整单总额只计一次；缺失订单或坏记录会禁用完整订单指标。
- 商品 ID 用于归组，不作为数值特征。数量单位、金额口径、时区不兼容的来源不能混算。
- `complete_coverage` 由用户确认；未确认的商品日保持未知，不擅自补零。
- `append` 拒绝日期重叠；`replace_overlap` 使用较新数据版本覆盖其整个日期范围，不按商品日期盲目去重。
- 提交时冻结来源哈希、字段版本、参数。后续上传、改字段、AI 重答不改变已发布报告。
- 报告 `products` 是完整商品结果；`attention_ids` 是去重后的完整待关注集合；`highlights` 只取前五个；`actions` 最多三条，同类事项合并。
- `forecast.quantity` 是未来七天累计销售参考，不是下月进货量，不是缺货情况下的真实需求。

产物在原 `storage/runs/{project_id}/{run_id}/`：

| 文件 | 内容 |
| --- | --- |
| `sales_report.json` | 完整冻结结果、来源、图表、商品、模型对照、建议 |
| `sales_products.csv` | 全部商品，非五件摘要；危险文本前缀作 CSV 保护 |
| `sales_row_audit.csv` | 原始版本与行号、纳入或排除原因 |
| `sales_backtests.csv` | 各预测起点、训练目标截止、实际及模型/基线值 |
| `manifest.json` | 原发布机制生成的数据、代码、环境和产物哈希 |

## API 与持久记录

- 来源信息：`GET /sales/sources/{version_id}`。
- 生成：`POST /sales/runs`；读取和取消继续用原 `/runs/{run_id}` API。
- 行动处理：`PUT /sales/runs/{run_id}/actions/{action_id}`，需要 `expected_revision`；过期修改返回 409。
- 商品核对：`PUT /sales/runs/{run_id}/item-notes`，记录本月整体或具体日期、店主选择的原因和备注，来源标为 `user_note`；同样使用 `expected_revision`。
- 查看记录：`GET /sales/runs/{run_id}/records`。
- 异常日原始行：`GET /sales/runs/{run_id}/item-records?item_id=...&day=...`；只接受本报告商品与月份，核对来源哈希，最多显示一百行但返回实际总数。
- 可选库存：`POST /sales/runs/{run_id}/inventory`，需要预测起点当天的明确库存、在途及确认。
- 备货公式：`ceil(max(0,预测销量+备用量-可售库存-确认到货量)/包装单位)*包装单位`。
- 导出：`GET /sales/runs/{run_id}/report?all_attention=true` 与允许列表中的 `/files/{artifact}`。
- AI：`POST /sales/runs/{run_id}/ask`，使用本次报告限定证据；数值占位符由程序绑定。结构、数值检查或模型失败会回退，不影响月报。
- 缺库存、成本或想凭销售表确定进货量的问题，优先按明确的数据限制回答，标为 `data_limit`，不冒充模型推断。

以上路径前缀均为 `/api/projects/{project_id}`。来源及运行 ID 均校验所属项目。不要新增直接接受绝对文件路径的分析接口。

正式验收只用真实公开数据：已下载的 Online Retail，以及明确注明来源的真实明细月汇总。Groceries 验证不适用销售月报的拒绝行为。没有编造商户库存、成本、日期或销售结果。

```bash

npm run build --prefix frontend
PYTHONPATH=backend .venv/bin/python -B scripts/accept_sales_public.py --output /home/ubuntu/changzihe/dev_work/RetailV2/recheck

```

最后一条会建立独立的真实月汇总验收项目并提交新任务，不要在繁忙服务器上反复执行。普通边界单元测试位于 `scripts/test_sales_v2.py`，它不是业务效果证据，也不是演示数据。

算法参数集中在 `sales_mining.py`：90 天预测历史、56 天异常历史、固定种子 42、固定时间窗、最多 1000 个模型回测商品。统计月报和完整待关注列表没有 1000 或五件上限。限制、被拒绝的覆盖和模型结果均写入报告。

Online Retail 的梯度提升预测没有超过四周平均法，网页按验证结果采用简单方法。独立 UCI 周销量实验仅略有改善，不等价于日级生产模型有效。异常没有商户真值标签，不能把警报数量当准确率。公开数据含批发、大单、运费等记录，不是已经验证过的小店经营方案。
