# 后续分析模块接入

质量引擎与持久任务机制已可使用。客户 RF/RFM 分群和商品共购已经按此边界接入；本文继续说明算法模块的输入约束和后续扩展原则。

## 读取可信输入

从已发布的质量运行出发，在服务端调用 `app.analysis_inputs.resolve_analysis_input(session, storage, project_id, quality_run_id, AnalysisParameters(...))`。函数检查项目归属、质量运行类型/终态、能力准入、manifest 上下文与选中视图的 SHA-256，返回路径、上下文、参数和质量清单。

不要直接读 S02 的 `canonical.parquet` / 金额候选表来跳过质量判断；也不能因为 `rfm_orders.parquet` 非空就默认可用。客户端只传 ID 和白名单参数，文件路径由服务端推导。

RF 使用 `rf_orders.parquet`，RFM 使用 `rfm_orders.parquet`。每行已是唯一订单，F 按订单数计算；M 用 Decimal 累加 `amount`，不再将同单总额或原始行金额相加。R 的参考时点依据业务设计确定为观察窗结束后的本地次日零点，或有效数据末日的次日零点，不使用机器当天日期。保存参考时点、时区、变换规则、数据/映射/策略/质量运行标识。

特征、K-means、候选 K、轮廓系数、稳定性与拒绝发布诊断属于分群模块。质量报告的输入可用不保证结果可发布；分群运行会再次判断特征差异、候选 K、簇规模、轮廓系数和稳定性。

关联使用 `basket_items.parquet`，其中单商品篮保留、同篮同商品唯一。规则分母与独立留出评测分母分别保存；词表、流行度、频繁项集和规则只从训练集获得，测试集只用于锁定后的补全评测。

## 扩展任务

1. 增加严格请求 schema 和后端提交入口；固定质量运行 ID、分析参数、随机种子、运行预算与幂等键，并校验项目归属和能力。
2. 在 `task_registry.py` 注册 kind、报告文件和全部必要产物，加入明确的任务分派与完成状态判定。不要使用动态 eval、任意模块名或客户端命令。
3. 扩展 `TaskRunner.execute` 的作业构造：当前只构造 quality 所需的 canonical/raw 输入。算法作业应调用上述输入解析器并传入固定有效视图，不能只增加 kind 后沿用质量输入。
4. 在独立任务子进程执行计算，复用两核/两线程、单并发、取消、超时、内存监控、完整产物发布和 manifest。API 请求中不做重计算。
5. 保存特征/结果/诊断与证据关联，声明新结果 schema；按 kind 分开前端类型与渲染。已有质量详情页不会渲染算法运行。
6. 补齐手算例、不适用例、真实数据例及中断/幂等回归，再更新 API 文档和阶段进度。

现有 `AnalysisRun` 已有 kind/parameters/result 等字段，但当前含必填 policy 等质量来源外键。新增算法时明确复用这些来源外键并补充 quality_run_id 关系，必要时做向前迁移；不可清空状态库或重写历史记录。当前 HTTP `/runs` 只接受质量请求，不把校验接口当作已完成的算法提交接口。

## 界面与验证

沿用项目上下文、数据与字段版本、运行历史和 teal/white 视觉规范。能力不足时给出业务原因和可采取的操作；功能未实现时不要展示假结果。专业用户界面不放部署地址、阶段编号、工具路径或开发提醒。

测试代码、测试数据库、截图与中间产物保存在正式项目外，测试工厂传入独立 database/storage/static 目录。默认关闭 Python 字节码及 pytest 缓存。正式代码保留运行所需模块与通用文档，路径相对于项目根目录。
